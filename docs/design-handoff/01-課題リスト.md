# 課題リスト — いま直したい9点

サイト運営者からの指摘を、設計者が判断できる粒度まで具体化したもの。
番号は指摘の順で、優先度順ではない。**★** が付いたものは影響範囲が大きい。

---

## 1. ★ 全体が単調。四角形が多すぎる

**症状**
見出しが四角い枠に囲われ、カードが四角、チップが四角、図表の枠も四角。
どのページも「角丸2〜3pxの矩形が並ぶ」という同じリズムで、
ページごとの性格の違いが視覚的に出ていない。

**なぜ悪いか**
学術的な密度のあるサイトで矩形だけを並べると、情報量の差が伝わらない。
「ここは一望する場所」「ここはじっくり読む場所」「ここは探す場所」の区別が消える。

**求めるもの**
- 矩形以外の構造要素を導入する（罫線そのもの、余白の断層、地の色の変化、縦組み、図版の抜き、傾き、重なり）
- ページの役割ごとに異なる視覚的リズムを与える
- 「囲う」以外の方法で要素を区切る。罫一本、間隔、書体の対比で十分なことが多い
- ただし**装飾のための装飾は不要**。この題材に軽薄さは合わない

---

## 2. ★★ 俯瞰マトリクスが全然だめ

**現状** → `現状コード/Matrix.astro`, `page-マトリクス.astro`
8つの時代（縦）× 6つの主題（横）＝48マスの表。各マスに記事本数を数字で入れ、
濃度で塗り分けている。マスをクリックすると下に記事一覧が出る。

**症状**
「データとして整理されている」だけ。人の目には**ただの数値マトリクス**に見える。
何を読み取ればいいのかが伝わらず、見て面白くない。

**なぜ悪いか**
このマトリクスはサイトの中核ナビゲーションであり、
「佐賀藩という対象を二つの軸で切ると何が見えるか」を体感させる装置のはず。
いまは Excel のピボットテーブルと変わらない。

**求めるもの**
- 表の体裁から離れてよい。48の交点が見渡せれば形式は自由
- 各交点が**何についての交点なのか**が、数字以外で伝わること
  （例：「藩制の成立 × 財政」は何の話なのか）
- 空白＝未執筆であることは引き続き隠さない。ただし「欠けている」ことが
  みすぼらしく見えるのではなく、**これから埋まる余地**として見えるように
- 記事が115本に増えたときも破綻しないこと（いまは5本しかない）
- 縦軸は時間なので、時間の流れが感じられるとよい

---

## 3. 記事本文の横幅が狭すぎる

**現状** → `現状コード/page-記事.astro`

```css
.article-grid {
  grid-template-columns: 220px minmax(0, 720px) 250px;  /* 目次 / 本文 / 欄外注 */
  gap: 56px;
  justify-content: center;
}
```

親の `.inner` が `max-width: 1200px` で頭打ちになっているため、
3カラムを収めると本文が 720px までしか伸びない。

**求めるもの**
- `.article-grid` を**画面幅いっぱい、またはPCの最大幅**まで広げる
- **左の目次と右の欄外注は非常に良いので必ず残す**。消さない
- 広げた結果、本文の一行が長くなりすぎないよう、文字サイズ・行長・
  カラム幅配分を設計し直すこと（日本語は一行40〜50字あたりが上限の目安）
- 1439px以下では欄外注を、1023px以下では目次を畳む現在の段階は維持してよい

## 5. ★ トップページの年表（1200–1877）がだめ

**現状** → `現状コード/page-トップ.astro` の `.spine` 一帯

8つの期間を横棒で並べ、その下に「藩が存在した区間」の線を引き、
さらに下に節目の出来事を点で打っている。点はホバーで題名が出る。

**症状**
横棒の集合でしかなく、677年という時間の長さも、
藩政264年がその中でどういう位置を占めるのかも伝わらない。
節目の点は小さすぎて、何が起きた時代なのかが読めない。

**求めるもの**
- トップに置く以上、**このサイトが何を扱っているのかが一目で分かる**こと
- 時間の長さと密度（藩政期に内容が集中していること）が体感できること
- 節目の出来事が、ホバーしなくても要点は読めること
- スマートフォンでも成立すること（現状は狭い画面で年号が消える逃げ方をしている）

## 6. ★★ 「家と家格」ページが全然だめ

**現状** → `現状コード/page-家と家格.astro`, `RankPyramid.astro`, `ChigyoChart.astro`

**症状**
家格ピラミッドが「幅の違う帯を11本積んだだけ」。
着到15組は数字カードが4枚並ぶだけ。知行高グラフは点と破線だけ。
どれも情報としては正しいが、**見て理解できる図になっていない**。

**求めるもの**
- 三家から足軽まで11段の序列が、**身分差として直感的に分かる**こと
- 同時に「これは本藩から見た序列にすぎず、三支藩・親類・親類同格は
  **独自の職制を別に持っていた**」という留保が、注記ではなく**図そのもので**伝わること
  （＝単一のピラミッドではない、という構造がこの図の要点）
- 各段にどの家が属するかが辿れること
- 知行高の推移は、記録のない年を「わからない」として正直に示しつつ、
  読み取れる図にすること

## 7. 年表がテキストだけではだめ

**現状** → `現状コード/page-年表.astro`

25件の出来事を縦に並べたリスト。年・和暦・題名・要約・タグ。

**症状**
文字だけが延々と続く。長い年表を読み通す動機がない。

**求めるもの**
- **1項目ごとではなく、2〜3項目ごとの区切りに図版・写真・図解を入れる**
- 区切りは恣意的でなく、意味のあるまとまり（時代の変わり目など）に置く
- 図版がまだ用意できていない箇所をどう扱うかも設計すること
  （写真は現時点で0点。当面は自作の図で埋めることになる）
- 主題での絞り込み機能は残す

## 8. ★★ 「人物と家」の構造そのものを作り直す

**現状** → `現状コード/page-人物と家.astro`
藩主の表（代数の二つの数え方を併記）＋その他人物のリスト。

**症状**
索引としても詳細としても中途半端。

**求めるもの — これは設計だけでなく情報構造の変更を伴う**

`/people/` を**検索・索引のページに徹させる**。ここには詳細を置かず、
主要なキーワードごとの個別ページへ送り出すことに専念させる。

送り先として想定するグループ：

| グループ | 個別ページの例 |
|---|---|
| 氏族・家 | 少弐氏 / 龍造寺氏 / **鍋島氏** |
| 鍋島氏の内訳 | **佐賀鍋島家**（本藩）/ **蓮池鍋島家** / 小城鍋島家 / 鹿島鍋島家 — それぞれ独立したページ |
| 龍造寺一門四家 | 多久家 / 武雄鍋島家 / 諫早家 / 須古鍋島家 |
| 親類三家 | 白石鍋島家 / 川久保神代家 / 久保田村田家 |
| 人のまとまり | 藩主 / 幕末の人物 / 明治政府の人物 / 学者・技術者 |

**家ごとの個別詳細ページには、基本情報に加えて地図を入れる。**
地図で示すもの：

- その家の**勢力範囲**（知行地・支配域）
- **関連する場所**（居城・陣屋・屋敷・菩提寺・窯など）
- 時期によって範囲が変わる家は、その変化も

**地図データは用意できた。**
近世村領域データから佐賀藩325村・小城藩68村・蓮池藩34村・鹿島藩11村（計399村）を
抽出済み（`src/data/datasets/villages.json`）。398村に座標がある。

ただし制約がある。詳細は `PROMPT-3-各ページ.md` の E を参照。

- 慶応4年（1868）の**一断面**であり、藩政264年を通じた領域ではない
- いまあるのは**点だけ**。面（ポリゴン）は農業集落境界データとの結合が必要で未了
- 背景地図（海岸線・郡界）も未取得。しかも**有明海の海岸線は干拓で動き続けた**ため、
  現代の海岸線を背景に置くと誤った印象を与える
- CC BY-SA 4.0 のため**出典表示が義務**
- 地図を持てるのは4家のみ。**少弐氏・龍造寺氏などには領域データが無い**

## 9. ★★ 職制図と家格ピラミッドを作り直す

**現状** → `現状コード/OfficeTree.astro`, `RankPyramid.astro`

**症状**
職制図は「角丸の箱を並べて細い罫でつないだだけ」。
組織の性格——請役所を頂点とする役方の階層、番方との並立、
文書行政（案文方）が独立して組み込まれていること、
最高責任者が旧主家一門から出るという変則——が何も見えない。

家格ピラミッドは 6 と同じ問題。

**求めるもの**
- **この二つは、このサイトの図表の水準を決める見本になる。**
  他の図はこの二つに揃える。だから最も力を入れてほしい
- 職制図：役方と番方が**並立**していること、役方が請役所を頂点とする
  階層であること、各機関が何をしていたかが、図を見るだけで分かること
- 家格ピラミッド：6 の要件を参照
- 両方とも、データ（家・役職の登録）が増えたときに自動で育つ構造なので、
  **要素数が2倍3倍になっても破綻しない**設計にすること
