## 1. 現状診断

| | 実測（2026-09-19） |
|---|---|
| 資料（`OCR全文/`） | 6冊・**4,537ページ**・約 8.8MB |
| サイト | 記事 **5本**・ソース 2,271行 |
| 資料の消化率 | **約 0.1%** |

**器の設計は良い。** `global.css` の和紙×墨トークン、`confidence` バッジによる学術的誠実性の表明、欄外注、Pagefind、View Transitions — この土台は捨てずに使う。

**問題は3点。**

1. **資料→記事のパイプラインが無い。** 8.8MB は一度に読めない。「引ける」状態にしない限り 115本は書けない。
2. **データモデルが `articles` 一本しかない。** 図表とアニメーションは**データの関数**である。人物・家格・知行・財政の構造化データが無い限り、どれだけ演出を書いても描く材料が無い。**ギアを上げる正体は演出ではなくデータ層。**
3. **OCR の質。** ページ全体が改行なしの一塊、`少弐`→`少式`、`竜造寺`/`龍造寺` の揺れ、註番号の崩壊（例：`(122)外山幹夫`）。**そのまま引用すると事実を誤る。** 原本 PDF での確認を工程に組み込む。

### 既存サイトの構造的限界

現行 `eras.ts` は佐賀藩260年を `edo` という **ID 1個**に収めている。ここに100本を入れると分類が崩壊する。さらに「請役所」のような制度記事は260年に跨がり、**どの時代にも属さない**。時代軸だけでは分類不能。

## 2. 情報構造の再設計 — 二軸 IA

記事を**時代軸**と**主題軸**の二軸で位置づける。

### 時代軸（8期）

| id | 名称 | 期間 | 記事目安 |
|---|---|---|---|
| `shoni` | 前史・少弐氏 | 〜1559 | 5 |
| `ryuzoji` | 前史・龍造寺氏と権力移行 | 1530–1607 | 10 |
| `seiritsu` | 藩制の成立 | 1607頃–1657 | 20 |
| `kakuritsu` | 藩制の確立と矛盾 | 1657–1750 | 22 |
| `mosaku` | 改革の模索 | 1750–1830 | 15 |
| `naomasa` | 直正の藩政改革 | 1830–1861 | 22 |

### 主題軸（6系統）

|---|---|---|

| `zaisei` | 財政・経済 | 借銀、二重会計、藩札、御用商人 |
| `gunji` | 軍事・対外 | 与と備、長崎警備、島原の乱、幕命普請 |
| `sangyo` | 土地・産業 | 干拓・新田、有明海、陶磁器、農政 |
| `bunka` | 学問・文化・宗教 | 葉隠、弘道館、医学、寺社 |

### これが生む新機能 — 俯瞰マトリクス

**8期 × 6系統 = 48セル**のマトリクスを、サイトのメインナビゲーションにする。

- 各セルに記事数と密度を表示。**空白セル＝未執筆**が一目で分かる
- 読者にとっては「制度を通史で追う」「一時代を全方位で見る」の両方の入口
- 制作者にとっては**進捗ダッシュボード**そのもの
- 書籍では絶対に作れない一覧性であり、「Webだからできること」の第一号になる

## 3. データ層の設計

**記事を書くときにデータを同時に出す。** 後からデータ化する方式は二度手間で必ず破綻する。これは工程上の絶対規則とする。

### コレクション（`src/content/`）

| コレクション | 主なフィールド | 用途 |
|---|---|---|
| `articles` | title, periods[], theme, sortYear, summary, confidence, sourceRefs[], related[] | 本文 |
| `people` | 名, 読み, 生没年, 家, 官位, 役職歴[], 関連記事[] | 人物ページ・系図 |
| `houses` | 家名, **家格**, 知行高（年次別）, 居所, 当主系譜 | 家格ピラミッド・知行サンキー |
| `offices` | 役職名, 所属機関, 定員, 職掌, 就任者[] | 職制図 |
| `events` | 年月日, 名称, 場所, 関係者[], 典拠 | 年表（**記事未執筆でも載る**） |
| `places` | 地名, 緯度経度, 郡, 現在の地名 | 地図 |
| `sources` | **書誌, 巻, 発行年, NDL URL** | 出典管理の要 |
| `terms` | 用語, 読み, 定義, 初出 | 用語集・本文ツールチップ |

### 出典管理の刷新（重要）

現行は `sources: ["『佐賀市史』第2巻 近世-1（研究ノート経由）"]` という自由文字列。これを**ID参照＋ページ番号**に変える。

```yaml
sourceRefs:
  - src: sogo-kenkyu      # sources コレクションの ID
    pages: "142-147"
  - src: sagashishi-2
    pages: "88"
```

得られるもの：

- 出典欄を**自動生成**（書誌の書式が全記事で統一される）
- 「この本のどのページを使ったか」の**逆引きページ**が作れる → 一般公開時の学術的信頼性が跳ね上がる
- 未照合箇所の機械的な洗い出しが可能になる

### 図表用データセット（`src/data/datasets/`）

記事とは別に、可視化専用のデータを置く。

- `kakaku.json` — 家格序列と所属家
- `chigyo.json` — 知行高の年次推移（三部上地の前後）
- `zaisei.csv` — 財政（収入・借銀・返済）※断片的にしか残らない前提で欠損を明示
- `nagasaki-keibi.csv` — 長崎警備の輪番と負担
- `kaigansen.geojson` — **干拓による海岸線の年代別ジオメトリ**
- `gunsei.json` — 与・備の編成

## 4. フェーズ計画

### Phase 0 — 基盤整備（1〜2週）

| # | 作業 | 成果物 |
|---|---|---|
| 0-1 | 現状の未コミット変更を整理してコミット | クリーンな `main` |
| 0-2 | **OCR 索引ツール**を書く | `tools/index-ocr.mjs` → `tools/out/ocr-index.json` |
| 0-3 | 目次 × ページ番号の対応表 | 章節→ページ範囲表 |
| 0-4 | 引用ルール・出典スキーマ確定 | `docs/CITATION.md` |
| 0-5 | 記事テンプレートと執筆手順書 | `docs/WRITING.md` |

**0-2 が計画全体の要。** 各 `## Nページ` を抽出し、人名・地名・制度語の出現位置を索引化する。「請役所について書きたい」→「総合研究 p.203, 211, 340／市史2巻 p.88, 92」が即座に引ける状態を作る。これが無いと Phase 2 は回らない。

索引ツールは**サイトリポジトリ内**に置く（Vault のルール：フォルダを勝手に増やさない）。

### Phase 1 — 情報構造の再設計（1〜2週）

- `eras.ts` → `periods.ts`（8期）＋ `themes.ts`（6系統）
- `content.config.ts` を8コレクションに拡張、`sourceRefs` 導入
- 既存5記事を新スキーマへ移行（`edo` → 適切な期＋主題）
- **俯瞰マトリクス**ページを実装（進捗ダッシュボード兼メイン入口）
- URL 設計を確定（`/period/<id>/`, `/theme/<id>/`, `/people/<id>/` …）
- **`Figure.astro`（出典・ライセンス必須）と画像最適化パイプラインを整備**（§6）
- 既存5記事に図版を入れ、**型A記事の見本を1本完成させる**（以後の基準になる）

### Phase 2 — コンテンツ量産（最長・数ヶ月）

**バッチ方式。1バッチ＝1主題群（例「藩財政」8本）。**

```
① 索引で該当ページを抽出
② そのページだけを精読（全文は読まない）
③ 疑義のある箇所は PDF 原本で確認
④ 記事 + エンティティ + データセット + 図版 を同時に産出
⑤ confidence を付与（sourced / ai / note）
```

**④ で図版まで作り切ること。** 「本文だけ先に書いて図は後で」は、結局どの数値を図にするつもりだったかを忘れて作り直しになる。読んでいる最中こそ図の材料が手元にある。

マイルストーン：

- **M1（30本）** 骨格 — 成立・制度・家臣団・直正改革の各中核
- **M2（70本）** 肉付け — 財政・産業・文化
- **M3（115本）** 完成 — 周縁と人物

### Phase 3 — 可視化（M1 以降、Phase 2 と並走）

データが揃ったセルから順に図表を実装。§5 のカタログ参照。

### Phase 4 — 体験設計

スクロール連動、時代間トランジション、目玉機能の作り込み。

### Phase 5 — 公開準備

出典の全件照合、パフォーマンス予算、アクセシビリティ監査、OGP/sitemap/JSON-LD、法務チェック（§8）。

## 6. 記事の型と図版方針

### 現状の実測（2026-09-19）

| 記事 | 本文 | 図版 |
|---|---|---|
| 三部上地 | 6,347字 | 0点 |
| 佐賀の乱 | 4,545字 | 0点 |
| 与と備 | 4,190字 | 0点 |
| 請役所 | 3,624字 | 0点 |
| 今山合戦 | 3,320字 | 0点 |

**文字数は既に目標（2,000字）を全て超えている。** 「薄い」と感じられる原因は文字量ではなく、**5本すべてで図版が1点も無いこと**。したがって対策は増量ではなく**図版の投入**であり、§3 のデータ層整備と同じ作業に帰着する。

### 記事の型

全記事を一律 2,000字にはしない。主題の重さに応じて3つの型を使い分ける。

| 型 | 本文 | 図版 | 想定本数 | 対象 |
|---|---|---|---|---|
| **A 主題記事** | 2,500〜4,000字 | 4〜6点 | 15 | 三部上地、藩財政、直正改革、干拓、長崎警備など中核テーマ |
| **B 標準記事** | 1,500〜2,500字 | 2〜4点 | 70 | 制度・事件・産業の個別テーマ |
| **C 小記事** | 600〜1,200字 | 1〜2点 | 30 | 人物、用語、単発の事件 |

型Cを許容することが重要。人物や用語を無理に 2,000字へ水増しすると、記述が薄まり `confidence` の維持ができなくなる。**短くて濃い記事は正しい成果物**とする。

### 図版の調達（一般公開のため権利処理が必須）

優先順位：

1. **自作 SVG 図版 — 最優先。** 職制図、系図、構造図、地図、グラフ。権利問題ゼロ、ダークモード対応可、テキストとして検索可能、そのままアニメーション化できる。**このサイトの図版の主力はここ**
2. **パブリックドメイン画像** — NDL デジタルコレクション（保護期間満了・インターネット公開のもの）の絵図・古地図・肖像、国立公文書館デジタルアーカイブ、ColBase（国立文化財機構）。**利用条件を1点ずつ確認し記録する**
3. **自分で撮影した写真** — 佐賀城本丸歴史館、三重津海軍所跡、築地反射炉跡、多久聖廟、有田、名護屋城跡ほか。権利は自分に帰属。現地取材の計画が別途必要
4. **書籍の図版 — 使用不可。** OCR 元の書籍に載る図表をスキャン・転載することはできない

> **4 の重要な例外：数値データの読み取りは可能。** 書籍の図表から石高・人口・財政などの**事実データを読み取り、自分の図として描き直す**ことは差し支えない（保護されるのは表現であってデータではない）。出典として「『佐賀藩の総合研究』p.XXX 掲載の数値より作成」と明記する。**これが §3 のデータセット構築の主な供給源になる。**

### 図版の実装要件

- `Figure.astro` コンポーネントを作る。**キャプション・出典・ライセンス表示を必須項目**にする（省略できない設計にして事故を防ぐ）
- 写真は Astro の `<Image>` で AVIF/WebP 化＋遅延読み込み。記事ページの JS 0KB は維持する
- SVG 図版は `currentColor` とトークン変数で描き、ライト／ダーク両対応
- すべての図版に代替テキスト。装飾目的の図版は作らない

## 8. 品質・法務ルール（一般公開の前提）

『佐賀藩の総合研究』（吉川弘文館 1981）、『佐賀市史』（佐賀市 1977）は**他人の著作物**。

1. **OCR 全文は公開しない。** 公開するのは「読んで構造化し直した自分の記述＋出典」のみ
2. 引用は必要最小限・明瞭区別・主従関係を守り、出典（書名・巻・ページ）を明示する
3. **`pdfpage://` リンクとローカルパス（`Y:\...`）を公開ビルドに絶対に出さない** → ビルド時の検出スクリプトで機械的に遮断する
4. `confidence` を厳守。原典と逐一照合したものだけが `sourced`
5. 断定できないことは「諸説あり」「未詳」と書く

### パフォーマンス予算

- 記事ページ：JS **0KB**（島を持たない）
- 可視化ページ：JS 100KB 以下（gzip）、D3 は必要モジュールのみ
- LCP 2.0s 以下、CLS 0.1 以下
- `prefers-reduced-motion` で全アニメーションを停止（現行方針を継承）

## 9. 次の着手

**Phase 0-1（現状コミット）→ 0-2（OCR 索引ツール）** から始める。

索引ができた時点で「請役所」「三部上地」で試験検索し、索引の実用性を確認してから Phase 1 に進む。
